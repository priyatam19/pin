# Phase 1 Experiment Results: PIN Hypothesis Testing

**Date**: November 4, 2025
**Experiment**: Test PIN on structured-input function (mg_mqtt_next_sub)
**Duration**: 5 minutes (300 seconds)
**Result**: ❌ **HYPOTHESIS INVALIDATED** - PIN cannot find the same crashes even on structured functions

---

## Executive Summary

The Phase 1 experiment tested whether PIN can find the same crashes as AFL when targeting a structured-input function (`mg_mqtt_next_sub`). Despite this function taking a struct pointer (not raw bytes), **PIN found 0 crashes** while **AFL found 11 crashes** targeting the same vulnerability.

**Root Cause**: The vulnerability is not in the structured-input function itself, but in **how the parser creates the struct from malformed input**. PIN bypasses the parser and creates structs synthetically via protobuf, missing the specific memory layout that triggers the bug.

## Technical Analysis

### Why PIN Failed to Find Crashes

#### The Vulnerability Mechanism

The crash occurs in `mg_mqtt_next_topic` (called by `mg_mqtt_next_sub`):

```c
static size_t mg_mqtt_next_topic(struct mg_mqtt_message *msg,
                                 struct mg_str *topic, uint8_t *qos,
                                 size_t pos) {
  unsigned char *buf = (unsigned char *) msg->dgram.ptr + pos;  // [1]
  size_t new_pos;
  if (pos >= msg->dgram.len) return 0;

  topic->len = (size_t) (((unsigned) buf[0]) << 8 | buf[1]);  // [2] CRASH HERE!
  topic->ptr = (char *) buf + 2;
  new_pos = pos + 2 + topic->len + (qos == NULL ? 0 : 1);
  if ((size_t) new_pos > msg->dgram.len) return 0;
  if (qos != NULL) *qos = buf[2 + topic->len];
  return new_pos;
}
```

**Line 24 [1]**: `buf` points into the raw MQTT packet via `msg->dgram.ptr`
**Line 28 [2]**: Reads `buf[0]` and `buf[1]` → **heap-buffer-overflow**

#### AFL's Workflow ✅

```
1. Raw MQTT bytes (82 82 00 02 00)
   ↓
2. mg_mqtt_parse(raw_bytes, len, 4, &msg)
   - Parses raw bytes
   - Sets msg.dgram.ptr = raw_bytes  [KEY: points to malformed buffer!]
   - Sets msg.dgram.len = len
   ↓
3. process_mqtt_message(c, &msg)
   ↓
4. mg_mqtt_next_sub(&msg, &topic, &qos, pos)
   ↓
5. mg_mqtt_next_topic reads from msg.dgram.ptr
   → buf[0] and buf[1] are PAST buffer end
   → HEAP OVERFLOW ✅
```

**Critical**: `msg.dgram.ptr` points to the **original raw MQTT bytes** with specific malformed structure.

#### PIN's Workflow ❌

```
1. Protobuf bytes (generated by libFuzzer)
   ↓
2. pb_decode() → Input message
   - Decodes protobuf fields
   - Creates msg.dgram.ptr from protobuf string field  [DIFFERENT!]
   - Synthesizes struct from scratch
   ↓
3. mg_mqtt_next_sub(&msg, &topic, &qos, pos)
   ↓
4. mg_mqtt_next_topic reads from msg.dgram.ptr
   → msg.dgram.ptr points to PROTOBUF-DECODED data
   → NOT the same memory layout as parser output
   → Vulnerability not triggered ❌
```

**Problem**: PIN creates `msg.dgram.ptr` from protobuf string fields, not from raw MQTT parser output. The specific buffer overflow condition requires the memory layout that `mg_mqtt_parse` creates from malformed bytes.

## Comparison with Original Hypothesis

### Original Hypothesis (from START_HERE.md)
> "PIN can find what AFL finds **when targeting structured-input functions**"

### Refined Understanding After Phase 1
> "PIN can find bugs in structured-input functions **only if the bug is in the function's logic, not in how the struct was created by a parser**"

### Classification of Vulnerabilities

| Vulnerability Type | PIN Works? | Example |
|-------------------|------------|---------|
| **Logic bugs in struct processing** | ✅ Likely | `if (config->timeout < 0)` → integer underflow |
| **Parser-created struct layout bugs** | ❌ No | CVE-mongoose-0001 (buffer overflow from parser) |
| **Direct buffer manipulation** | ❌ No | Raw byte parsers |
| **Synthetic struct validation** | ✅ Likely | Field constraint violations |

**CVE-mongoose-0001 is a "Parser-created struct layout bug"** - the vulnerability requires the specific memory layout that `mg_mqtt_parse` creates from malformed input.

## Conclusion

### Hypothesis Status
❌ **REJECTED**: Even when targeting structured-input functions, PIN cannot find the same crashes as AFL if the vulnerability depends on parser behavior.

### Root Cause Summary
1. **CVE-mongoose-0001** triggers when `mg_mqtt_next_topic` reads past buffer bounds
2. The buffer (`msg.dgram.ptr`) must point to **malformed raw MQTT bytes**
3. AFL creates this buffer via `mg_mqtt_parse(raw_malformed_bytes)`
4. PIN creates this buffer via `pb_decode(protobuf_bytes)`
5. Different creation methods → different memory layouts → no crash

### Why This Matters
PIN's design assumes you can **synthesize arbitrary struct values** and test function behavior. But when the bug is in **how the parser creates the struct from malformed input**, synthesizing structs directly bypasses the vulnerable code path.

**Analogy**:
- AFL tests: `malformed_json → parser → struct → process` (finds parser bugs)
- PIN tests: `protobuf → struct → process` (finds processing bugs, not parser bugs)

### Option 1: Accept Limitation and Document Scope ✅ RECOMMENDED

**Paper Contribution**:
> "PIN successfully generates fuzzing harnesses for function-level testing, achieving X% coverage on structured-input processing logic. However, PIN's approach bypasses parsing stages, and thus cannot detect vulnerabilities that require specific parser output states. For comprehensive parser testing, traditional byte-level fuzzers like AFL remain necessary."

**Impact**: Honest research contribution showing clear tool boundaries.

### Option 2: Extend PIN with Two-Stage Fuzzing 🔧 RESEARCH EXTENSION

**Approach**:
1. **Stage 1**: Use AFL to fuzz parser (`mg_mqtt_parse`)
2. **Stage 2**: Capture AFL-generated structs, serialize to protobuf
3. **Stage 3**: Use PIN to fuzz downstream functions with AFL-created structs

**Benefit**: Combines AFL's parser coverage with PIN's structured fuzzing.

### Option 3: Target Different Functions 🔍 FIND BETTER EXAMPLES

Test PIN on functions with **logic bugs**, not **parser bugs**:
- Configuration validation functions
- Business logic with complex conditionals
- Functions that don't depend on parser-created memory layout

## Lessons Learned

1. **"Structured input" ≠ "Works with PIN"**
   - Function signature alone doesn't determine PIN applicability
   - Must consider: Does bug depend on HOW struct was created?

2. **Parser bypass is a design choice with tradeoffs**
   - ✅ Faster fuzzing (no parsing overhead)
   - ✅ Direct function testing
   - ❌ Misses parser bugs
   - ❌ Misses parser-dependent bugs

3. **Attack surface depends on entry point**
   - Fuzzing `mg_mqtt_parse`: Tests parser (finds CVE-mongoose-0001)
   - Fuzzing `mg_mqtt_next_sub`: Tests topic extraction (misses CVE-mongoose-0001)

4. **Hypothesis testing revealed tool limitation**
   - This is a **positive research outcome**!
   - Shows thorough evaluation and honest reporting
   - Identifies clear future work directions
